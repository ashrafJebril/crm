# SP-19 Channels Hub and Multiple Numbers: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- **One channels hub.** A new `channels` screen lists every connected channel (WhatsApp numbers, Facebook, Instagram, TikTok, Telegram bots, website chat). Each has a status badge, a detail view and actions (rename, make default, reconnect, disconnect). "Add channel" starts each connect flow. The channel cards in `IntegrationsTab.tsx`/`ZernioCard.tsx` move here.
- **Several WhatsApp numbers per workspace.** Every number is its own `Channel`. Inbound on number B lands in B's conversations. Replies go out from the number the conversation belongs to. The inbox gets number tabs and a "Number" filter (SP-01's deferred `number*` filter).
- **One-click WhatsApp signup through Meta** (embedded signup), with landline verification and a plan-based number limit. When the Meta app config is missing, the button is hidden and the hub gives the reason.
- **Website chat widget.** An embed snippet (`<script>` loader) plus a hosted chat page link. Visitors chat with the inbox in real time. Foreign origins are rejected and requests are rate-limited.
- **Telegram channel.** Connecting a bot token registers the webhook. The webhook validates Telegram's `secret_token` header.

**Architecture:**
- **`Channel` is the routing source of truth; `Integration` stays.**
  - The deployed code on `main` reads and writes `Integration` (`@@unique([workspaceId, platform])`), and the migration runs before this code ships. So `Integration` and its unique constraint are untouched.
  - Each `Integration` gets exactly one `Channel` with `integrationId` set. The SQL backfill creates them, and `ChannelsService.ensureLegacyChannels` creates any that rows written by `main` after the migration are missing. Both use the same deterministic mapping.
  - Credentials of a legacy channel keep living on its `Integration` row. Channels with no `Integration` (a second Meta number, Telegram) keep their credentials in `Channel.secretsEnc`.
- **Conversations know their channel.**
  - `Conversation.channelId` is nullable. The backfill sets it wherever it can be derived: one `Integration` per platform, so `conversation.channel` → that integration's channel.
  - When reading a row whose `channelId` is null, the code falls back through `ChannelResolver.effectiveChannel(conv)` (Global Constraints). The resolved id is written back lazily.
  - The conversation key for inbound becomes `(workspaceId, contactId, channelId)` instead of `(workspaceId, contactId, channel)`, so one contact who writes to two numbers has two conversations. The contact itself is shared, because `Contact` stays unique on `(workspaceId, externalSource, externalId)`.
- **Inbound routing by provider account.** Each webhook resolves its channel in one place: `ChannelResolver.forInbound(provider, externalId)`. The provider ids are:
  - Zernio: `account.accountId`
  - Meta WhatsApp: `metadata.phone_number_id`
  - Telegram: the `:channelId` in the path
  - web chat: `:channelId`

  If no channel matches but a matching legacy `Integration` does, the resolver mirrors it and goes on, so nothing that `main` connected is dropped.
- **Outbound by channel.** Every send path resolves the conversation's effective channel and uses that channel's credentials. The paths are the Zernio text and template sends, the Meta WhatsApp text and template sends, the AI reply, the workflow `send-whatsapp-template` executor and the campaign send.
  - Zernio sends use `channel.externalId` as the `accountId`.
  - Meta sends use `channel.externalId` as the `phone_number_id`, plus the channel's token.
  - The new native channels (Telegram, web chat) send through one route, `POST /conversations/:id/send`, backed by a `ChannelTransport` registry.
- **Shared inbound sink for new channels.** `InboundSinkService.record(...)` writes the contact, conversation and message, emits realtime and fires the same side effects as the Zernio path (`pipelineAutomation.onInboundMessage`, `WORKFLOW_TRIGGER_EVENT` `message_received`). Telegram and web chat use it. The Zernio and Meta ingest paths only get the channel-aware lookup in SP-19; they are not refactored onto the sink, to limit regression risk.
- **Web chat runs in an iframe served by the API host.**
  - The loader `GET /api/widget.js` injects a bubble and an iframe that points at the hosted chat page, `GET /api/chat/:channelId?embed=1&parent=<origin>`.
  - The chat page runs on the API origin, so its `fetch` and socket calls are same-origin. No CORS change is needed.
  - The allowed-origin list is enforced twice. The page sends a `Content-Security-Policy: frame-ancestors <allowedOrigins>` header, so the browser refuses to frame it elsewhere. The widget API also checks the `Origin` header: it accepts only the API's own origin, and checks the claimed `parent` against `allowedOrigins`.
  - Live replies arrive through a new socket.io namespace, `/widget`, with one room per visitor. A REST poll is the fallback.
- **Telegram.** `getMe` validates the token. `setWebhook` registers `${PUBLIC_BASE_URL}/api/webhooks/telegram/:channelId` with a random `secret_token`. Only a SHA-256 hash of that secret is stored. The bot token is stored encrypted.
- **Embedded signup.** The hub asks `GET /channels/whatsapp/embedded-signup/config` whether the flow is available. The frontend loads the FB JS SDK only when it is, using `appId`/`configId` from that response; no `VITE_` variables are needed. The backend exchanges the `code` (existing `embeddedSignupExchange` logic, moved to be channel-aware), subscribes the app to the WABA and registers the number. A WABA with no usable number becomes a `pending` channel driven by the landline card.

**Tech Stack:** NestJS 10, Prisma 5, socket.io 4 (namespace `/widget`), jest; React 18, vitest. No new dependencies. Rate limiting is a small in-memory limiter, the widget is vanilla JS, and the Telegram Bot API is called with `fetch`.

**Spec:** roadmap §2.7 and §SP-19. Also SP-01's "number filter turns on with SP-19", and the consumers SP-12 (`CampaignRecipient.channelId`), SP-13 (`senderChannelIds`, per-number split) and SP-14 (`Channel.health`, `POST /channels/:id/health/check`).

## Global Constraints
- **Data (exact names; SP-12/13/14 build on them):**
  ```
  model Channel {
    id                String    @id @default(cuid())
    workspaceId       String
    kind              String    // whatsapp | telegram | webchat | facebook | instagram | tiktok (others, e.g. snapchat, stored verbatim)
    provider          String    // zernio | meta | telegram | native (legacy Integration.provider values copied verbatim, e.g. "kapso")
    externalId        String?   // zernio accountId | Meta phone_number_id | Telegram bot id | null for webchat
    displayName       String
    phoneNumber       String?   // E.164 for WhatsApp, when known
    status            String    @default("active") // active | pending | needs_attention | disconnected | error
    statusReason      String?
    health            Json?     // reserved for SP-14: {quality, tier, nameStatus, verified, checkedAt, issues[]}; SP-19 leaves it null
    isDefault         Boolean   @default(false)
    config            Json?     // NON-secret settings: widget {allowedOrigins[], greeting, greetingAr, color, position, askName}, meta {wabaId, verification}, telegram {botUsername}
    secretsEnc        String?   // encryptSecret(JSON) of {accessToken?, botToken?, registrationPin?}; never selected into a DTO
    webhookSecretHash String?   // sha256 hex of the Telegram secret_token
    integrationId     String?   @unique  // legacy link, FK Integration onDelete SetNull
    lastInboundAt     DateTime?
    disconnectedAt    DateTime?
    createdAt         DateTime  @default(now())
    updatedAt         DateTime  @updatedAt
    @@unique([workspaceId, provider, externalId])
    @@index([workspaceId, kind])
    @@index([provider, externalId])
  }
  ```

  - `Campaign.senderChannelId String?` (FK `onDelete: SetNull`).

- **Migration:**
  - File: `backend/prisma/migrations/20261112120000_channels/migration.sql`. Hand-written and applied with `npx prisma migrate deploy` only.
  - Additive and idempotent: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE [UNIQUE] INDEX IF NOT EXISTS`, and every FK inside `DO $$ BEGIN … EXCEPTION WHEN duplicate_object THEN NULL; END $$`.
  - Constraint and index names follow Prisma's conventions: `Channel_pkey`, `Channel_workspaceId_fkey`, `Channel_integrationId_fkey`, `Channel_integrationId_key`, `Channel_workspaceId_provider_externalId_key`, `Channel_workspaceId_kind_idx`, `Channel_provider_externalId_idx`, `Conversation_channelId_fkey`, `Conversation_workspaceId_channelId_idx`, `Campaign_senderChannelId_fkey`. The SQL-only `Channel_one_default_per_kind` is `CREATE UNIQUE INDEX IF NOT EXISTS … ON "Channel"("workspaceId","kind") WHERE "isDefault"`.
  - It is safe for the deployed code because it adds only nullable columns and a new table. `Integration` is not altered.
  - **Backfill, which can be rerun:**
    1. Run `INSERT INTO "Channel" (…) SELECT 'chi_' || i."id", i."workspaceId", lower(i."platform"), i."provider", i."pageId", COALESCE(NULLIF(i."pageName", ''), initcap(i."platform")), 'active', NOT EXISTS (SELECT 1 FROM "Channel" d WHERE d."workspaceId" = i."workspaceId" AND d."kind" = lower(i."platform") AND d."isDefault"), i."id", i."createdAt", CURRENT_TIMESTAMP FROM "Integration" i WHERE NOT EXISTS (SELECT 1 FROM "Channel" c WHERE c."integrationId" = i."id") ON CONFLICT DO NOTHING;`.
       - The id is deterministic.
       - It never parses `Integration.raw`, because a malformed JSON row would abort the migration. The code fills in `phoneNumber` on the next sync.
    2. Run `UPDATE "Conversation" cv SET "channelId" = ch."id" FROM "Channel" ch JOIN "Integration" i ON i."id" = ch."integrationId" WHERE cv."channelId" IS NULL AND cv."workspaceId" = i."workspaceId" AND lower(cv."channel") = lower(i."platform");`.
       - `webchat` and `l` conversations stay null.
       - Every batch is limited by `channelId IS NULL`, so a rerun is a no-op.
  - The TS function `channelFromIntegration(i)` in `backend/src/channels/legacy-mirror.ts` mirrors the SQL mapping exactly, and a spec pins the two together.
- **Credentials and secrets:**
  - Stored the way `Integration.accessToken` is stored today: `encryptSecret`/`decryptSecret` from `backend/src/common/token-crypto.ts`. That is AES-256-GCM when `TOKEN_ENC_KEY` is set and plaintext otherwise. The Telegram `secret_token` is stored only as a SHA-256 hash. The Meta registration PIN goes inside `secretsEnc`.
  - DTOs are built by one whitelist function, `toChannelDto(row)`: `{id, kind, provider, externalId, displayName, phoneNumber, status, statusReason, isDefault, config (secret-free subset), lastInboundAt, createdAt, conversationCount?}`. `secretsEnc`, `webhookSecretHash`, `integrationId`, tokens and verify tokens are never returned.
  - Telegram URLs carry the token in the path (`/bot<token>/…`). Extend `redactUrl` (`backend/src/common/redact-url.ts`) to mask `/bot[^/]+/`. All Telegram and Graph errors go through it before logging. Never log request bodies that contain `botToken`, `code` or `accessToken`.
- **Effective channel for null `channelId`** (`ChannelResolver.effectiveChannel`): use the conversation's own `channelId`. Otherwise use the active channel linked to the workspace's legacy `Integration` for `conv.channel`, which is what `main` used to send from. Otherwise use the default channel of that kind. Otherwise there is none: reads still work, and sends return 409 `channels.not_connected`. When the resolver picks a channel it writes `channelId` back, but only while it is still null (`updateMany where channelId: null`).
- **Disconnected channels:**
  - `DELETE /channels/:id` is a soft disconnect: `status = "disconnected"`, `disconnectedAt` set, provider-side teardown done as far as possible. Conversations keep their `channelId`.
  - Sending on a disconnected channel returns 409 `channels.disconnected`. It never falls back silently to another number.
  - Reconnecting the same provider account (same `externalId`) reactivates the row.
- **Default channel:** at most one per `(workspaceId, kind)`. Make default with `PATCH {isDefault:true}`, which clears the others in one transaction. Only an `active` channel can be the default (409 `channels.default_requires_active`). The first active channel of a kind becomes the default automatically.
- **Number limit (WhatsApp):**

  - The limit counts non-disconnected WhatsApp channels. It gates only our add flows (embedded signup, manual token, Zernio connect link), with 409 `channels.limit_reached {limit, plan}`.
  - Accounts that already exist at the provider (a Zernio sync) are always mirrored. Inbound is never dropped because of the limit.

## Review Focus
1. **Number B isolation.** A message to number B (Zernio account B, or Meta phone id B) must:
   - create or reuse a conversation with `channelId = B` (a contact who also writes to A keeps a separate A conversation);
   - be replied to through account B;
   - never touch A's conversation.

   A legacy null-`channelId` conversation is adopted only by the channel `effectiveChannel` resolves to.

   Test: `inbound on number B lands in B's conversations`, with both providers, plus `reply from B's conversation sends through B's account`.
2. **Migration mapping and safety.**
   - Every `Integration` maps to exactly one `Channel`, and a rerun creates nothing.
   - At most one default per kind.
   - Conversations are backfilled only where derivable.
   - The SQL never touches `Integration` and never parses `raw`.
   - The TS mirror matches the SQL mapping.

   Test: `migration maps each Integration to one Channel`.
3. **Secrets never leave the server.** Every `/channels*` response and every public widget response, serialized to JSON, contains no `secretsEnc`, `webhookSecretHash`, `accessToken`, `botToken`, `verifyToken` or `integrationId`, and no value equal to a test token. Logged Telegram and Graph errors have the token masked. Test: `channel DTOs and logs never contain secrets`.
4. **Public endpoints are tight.** Tests:
   - `widget rejects foreign origin`: 403 for a foreign `Origin` and for a foreign `parent`; 200 for the API origin with an allowed parent.
   - `widget rate limit returns 429`.
   - `widget visitor token required to read history`.
   - `telegram webhook secret validated`: 403 for a missing or wrong header, 200 and ingest for the right one, 404 for an unknown or disconnected channel.
5. **Disconnect never reroutes.** Sending in a conversation whose channel is disconnected returns 409 `channels.disconnected`, and nothing is sent from another number. Disconnecting a Telegram channel calls `deleteWebhook`. Test: `send on disconnected channel is refused`.
6. **Visibility composes.** `GET /conversations?channelId=B` for an assigned-only agent returns only their assigned B conversations. `POST /conversations/:id/send` on a hidden conversation returns 404. Test: `number filter composes with conversationScope`.

## Architecture Rulings and Risks
Each item below names the risk, then the recommended ruling. Items marked **(needs controller ruling)** are repeated in Open Questions.

1. **"Channel replaces the Integration unique limit" cannot mean dropping or altering `Integration` in SP-19.** `main` still reads `Integration` on every send and webhook, and the migration runs before this code ships.
   - **Ruling:** keep `Integration` (and its unique constraint) as the legacy credential store for channels that `main` connected. Mirror rows lazily (`ensureLegacyChannels`), and write new connections to `Channel` only.
   - A follow-up cleanup SP may copy legacy credentials into `secretsEnc` and drop the dependency, after SP-19 is live.
2. **Zernio collapses several accounts of one platform into one `Integration` row** (`syncAccounts` picks a "primary"). Inbound for the other accounts is dropped today with `Inbound for unknown zernio accountId`.
   - **Ruling:** `syncAccounts` keeps upserting the single `Integration` row, for `main` compatibility. It also upserts one `Channel` per Zernio account (`provider "zernio"`, `externalId = account._id`), marking accounts that Zernio no longer lists as `disconnected`.
   - **Risk:** it is unverified whether Zernio's hosted connect lets one profile connect a *second* WhatsApp number. T1 includes a read-only live check (`GET /integrations/zernio/whatsapp/numbers` and `listAccounts`). If Zernio allows only one WhatsApp account per profile, the multi-number path is Meta direct (T4) only. **(needs controller ruling / Zernio confirmation)**
3. **`resolveZernioTarget` finds the Zernio conversation by listing every conversation of the platform and matching `participantId`.** With two accounts, the same customer can match the wrong account's conversation.
   - **Ruling:** filter the listing by `accountId === channel.externalId`, and store `externalId` per conversation (already done once resolved).
4. **Manual Meta connect overwrites the single WhatsApp `Integration`** (`WhatsAppService.connect` → `find(workspaceId)`). Connecting a second number today silently replaces the first.
   - **Ruling (T4):** when a Meta WhatsApp `Integration` already exists for a different `phone_number_id`, create a `Channel`-only row with `secretsEnc` instead of updating the `Integration`.
5. **Templates are per WABA, and `Template` has no `channelId`.** Numbers on different WABAs can have different approved templates.
   - **Ruling:** SP-19 keeps template sync and listing on the default WhatsApp channel. Template sends from a conversation go through that conversation's channel, and a provider "template not found" surfaces as the provider's error.
   - Per-number templates belong to SP-13/SP-14. Note it there.
6. **Campaigns run as Zernio broadcasts only.**
   - **Ruling:** `Campaign.senderChannelId` is honoured only when it is an active Zernio WhatsApp channel of the workspace (else 400 `channels.sender_invalid`). Null means the default WhatsApp channel, which is today's behaviour.
   - The sender picker UI is SP-13. SP-19 only adds the column, the DTO field and the backend check.
7. **CORS.** The global `enableCors` allows only `CORS_ORIGIN`, and the realtime gateway shares that list. A cross-origin widget calling the API directly would need a per-route CORS delegate.
   - **Ruling:** use the iframe architecture (hosted page on the API origin), which needs no CORS change, plus CSP `frame-ancestors` and the `Origin`/`parent` checks.
   - This deviates from the roadmap's `public/widget.js` (frontend host): the loader is served by the backend at `GET /api/widget.js`, so it can derive the API base from its own `src`, and it ships and versions together with the widget API. **(needs controller ruling — confirm the deviation)**
8. **Socket.io for visitors.** The existing gateway requires a member JWT on the default namespace.
   - **Ruling:** use a separate `WidgetGateway` (namespace `/widget`, same `path: "/api/socket.io"`) with its own handshake check. The hosted page loads the socket.io client from `/api/socket.io/socket.io.js`, which socket.io serves by default.
   - If that file is not served in production, the page falls back to polling `GET /widget/:id/messages?after=` every 4 seconds. The verification task checks which one is active.
9. **Rate limits are per machine** (in-memory, no Redis). `fly.toml` runs `min_machines_running = 1`, so this is acceptable now. Document that scaling out multiplies the effective limit.
10. **Secrets at rest** depend on `TOKEN_ENC_KEY`. It is not present in the dev `.env`, and whether it is set in Fly secrets is unknown.
