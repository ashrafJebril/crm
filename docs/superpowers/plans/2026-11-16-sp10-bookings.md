# SP-10 Bookings: Services, Staff, Availability, Board — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- **Services catalog.** A workspace defines services: name (EN/AR), colour, duration, optional price and currency, which staff provide it, and active/archived. Deleting a service that bookings reference **archives** it instead (roadmap acceptance `delete-service-with-references archives instead`, Review Focus 2).
- **Staff resources.** A staff resource has a name, a role label, an optional link to a workspace member, a **weekly working schedule** (`{mon:[{from,to}], …}`), the services it provides, and active/archived. Cards and a table, with search.
- **Schedule fit and availability.** A booking placed on a resource must fit wholly inside one of that resource's working windows on that weekday, **in the workspace timezone** (acceptance `schedule-fit rejects outside hours in workspace TZ`). `GET /bookings/availability` lists the free slots of a service (and optionally one resource) on a date.
- **No double booking.** Creating or rescheduling a booking checks fit and overlap inside one transaction under a per-resource advisory lock; the loser of two concurrent writes gets 409 `SLOT_TAKEN` with the booking that won (acceptance `slot-race.spec.ts`, Review Focus 4). A stale edit (version mismatch) gets 409 with the current row.
- **Lifecycle.** Status changes follow one transition table: `pending → confirmed | cancelled`, `confirmed → completed | no-show | cancelled`; `completed`, `cancelled`, `no-show` are final (acceptance `illegal transition completed→pending rejected`).
- **Bookings UI.** The Calendar screen gains a **board** (kanban by status, drag only along allowed transitions), an **agenda** view with booked minutes per day, a **reschedule** dialog (slots + fit), a **service and staff filter**, a **booking search** typeahead, and **view/date/filters in the URL**.
- **Catalog import.** A wizard imports services and staff from pasted text, a website URL or a file (per-kind `.xlsx` templates, or any CSV/XLSX). Free-form input goes through AI extraction; the review step lists proposed rows with **duplicates unchecked**; the run is a resumable background job.
- **HJZ keeps working.** Bookings mirrored to HJZ (`HjzAppointmentSyncService`) keep their payload: `service`/`serviceAr` stay as name snapshots and `staffId` keeps the member link. The `hjz-sync` specs are a regression gate.

**Architecture:**
- **Data and the legacy shape.** `Appointment` keeps `service`, `serviceAr`, `staffId` and every HJZ column. New nullable `serviceId`, `resourceId` and a `version` counter are added. A catalog booking writes **both**: the ids, and the service's current names into `service`/`serviceAr` and the resource's `userId` into `staffId`. Legacy rows (no ids), rows created by the deployed `main`, and the AI agent's MCP bookings without ids keep working unchanged.
- **Time** (`backend/src/bookings/booking-time.ts`, pure, built on SP-04 `activities/buckets.ts` `validTz`/`localMidnight`):
  - `wallClock(instant, tz) → {dateISO, minutes, weekday: "mon".."sun"}`;
  - `instantOf(dateISO, minutes, tz) → Date` (DST-correct through `localMidnight` + offset re-check);
  - the workspace timezone is `Workspace.timezone` through `validTz` (invalid → `Asia/Riyadh`).
- **Schedule** (`backend/src/bookings/schedule.ts`, pure; frontend mirror `src/screens/calendar/schedule.ts`, the two pinned by a shared fixture test):
  - `WeeklySchedule = Partial<Record<"mon"|"tue"|"wed"|"thu"|"fri"|"sat"|"sun", {from: "HH:MM", to: "HH:MM"}[]>>`.
  - `validateSchedule(json)`: only those keys; ≤ 3 windows a day (`MAX_WINDOWS_PER_DAY`); `HH:MM` from `00:00` to `24:00` (`24:00` only as `to`); `from < to`; windows sorted and not overlapping. Overnight shifts are split across two days (ruling 6). Anything else is 400 `bookings.schedule_invalid {day, index, reason}`.
  - `scheduleFit(schedule, {dateISO, startMin, endMin}) → {kind: "ok"} | {kind: "off_day", day} | {kind: "outside_hours", day, windows}` (Tkana `fitWorkingWindows`): the booking fits when `start >= from && end <= to` of **one** window; ending exactly at `to` fits. A schedule with no window on any day is **unconfigured** and fits everything (ruling 6). A booking that crosses local midnight is `outside_hours`.
- **Availability** (`backend/src/bookings/availability.ts` pure + `bookings.service.ts`):
  - Input: `serviceId`, optional `resourceId`, `date` (`YYYY-MM-DD`, workspace-local). Candidate resources = active, non-archived resources linked to the service (or the one given, which must provide it: 400 `bookings.resource_not_offering`).
  - Per resource: for each window of the date's weekday, starts from `from` in steps of `SLOT_STEP_MIN = 15` while `start + durationMin <= to`; drop starts before `now` (no lead time, ruling 7); drop starts overlapping a **blocking** booking.
  - **Blocking** = `status IN ('pending','confirmed')` and (`resourceId = R` **or** (`resourceId IS NULL` and `staffId = R.userId`)) — legacy, agent and HJZ-mirrored bookings of the same member block too (ruling 4).
  - Overlap: `a.start < b.end && a.end > b.start` (back-to-back is fine). No buffers (ruling 7).
  - An unconfigured schedule offers **no** slots (there is nothing to offer) but does not block a manual booking.
  - Output: `{date, tz, slots: {startAt: ISO with offset, resourceId}[]}`, at most 200; `date` more than `MAX_DAYS_AHEAD = 365` days ahead or in the past → 400 `bookings.date_invalid`.
- **Writes** (`backend/src/bookings/booking-writer.ts`, used by `AppointmentsService.create/update` so the REST routes and the MCP tools share it):
  1. Resolve the service (by `(serviceId, workspaceId)`, active; archived → 400 `bookings.service_archived`) and the resource (by `(resourceId, workspaceId)`, active). Unknown/foreign ids → 404 `bookings.service_not_found` / `bookings.resource_not_found`.
  2. **Resource resolution for legacy callers (ruling 4):** when no `resourceId` is given but `staffId` names a member who has an active `StaffResource`, that resource is used, so the agent and the old Calendar dialog cannot double-book a member who is in the catalog.
  3. `durationMin` defaults to the service's; `service`/`serviceAr` default to the service's names; `staffId` = the resource's `userId` when set.
  4. **Fit gate** when a resource is resolved and the write is not `bypassFit` (ruling 5): not `ok` → 422 `bookings.outside_schedule {fit}`.
  5. In `prisma.$transaction`: `SELECT pg_advisory_xact_lock(hashtext('booking-resource:' || $resourceId))`; re-read blocking bookings of that resource (and its member) overlapping `[startAt, startAt + durationMin)` excluding the row itself → any → 409 `SLOT_TAKEN {conflict: {id, startAt, durationMin, status}}`; then insert/update. On update, the `version` check runs inside the same transaction (`updateMany where {id, workspaceId, version}`; 0 rows → 409 `bookings.version_conflict {current}`) and increments `version`.
  6. After commit: `hjzSync.changed(id)` (unchanged), the `appointment_completed` workflow event on a transition into `completed` (unchanged).
  - Without a resolved resource (legacy free-text booking with no catalog member) there is no gate and no lock, exactly as today.
- **Transitions** (`backend/src/bookings/booking-status.ts`, pure; frontend mirror `src/screens/calendar/bookingStatus.ts`):
  ```ts
  export const BOOKING_ALLOWED: Record<AppointmentStatus, AppointmentStatus[]> = {
    pending: ["confirmed", "cancelled"],
    confirmed: ["completed", "no-show", "cancelled"],
    completed: [], cancelled: [], "no-show": [],
  };
  ```
  A same-status write is a no-op, not an error. Any other change → 409 `bookings.illegal_transition {from, to, allowed}`, for every caller (REST, MCP `update_appointment`/`cancel_appointment`). Time, duration or resource changes are allowed only while `pending`/`confirmed` (409 `bookings.closed`). The existing status values (with the hyphen in `no-show`) are kept (ruling 8).
- **Conflicts are shown, not hidden.** List rows carry `conflict: boolean` (another blocking booking of the same resource or member overlaps) and `fit: "ok" | "off_day" | "outside_hours" | "unchecked"` (unchecked when no resource). Rows created before SP-10, by `main` or with `bypassFit` show their conflicts on the board and agenda.
- **Delete with references** (`services.service.ts`, `staff.service.ts`):
  - `GET /services/:id/delete-preview` → `{bookingCount, upcomingCount, staffCount}`; `GET /staff/:id/delete-preview` → `{bookingCount, upcomingCount, serviceCount}`.
  - `DELETE /services/:id`: any `Appointment.serviceId` reference (any status) → archive (`active = false`, `archivedAt = now`, staff links kept) → `{archived: true, bookingCount}`; none → delete (links cascade) → `{deleted: true}`. The same for `DELETE /staff/:id`. Both run under the resource/service advisory lock so a booking created concurrently is either seen (archive) or refused (`service_archived`).
  - FKs `Appointment.serviceId`/`resourceId` are `ON DELETE SET NULL` as a backstop; the name snapshot in `service`/`serviceAr` keeps the booking readable.
- **Catalog import** (`backend/src/catalog-import/`, ruling 1):
  - Own table `CatalogImport` (not `ImportJob`; ruling 1 explains why). States: `extracting → review → running → done | failed | cancelled`.
  - **Inputs:** `paste` (≤ 200 000 chars), `url` (one page, ruling 9), `file` (CSV/XLSX through SP-03 `parseFile`, 10 MB, 2 000 rows). A file whose header row matches a per-kind template exactly is parsed **deterministically** (no AI); anything else is flattened to text and sent to extraction.
  - **Extraction:** `CatalogExtractor` interface; `AnthropicCatalogExtractor` uses the Anthropic Messages API by `fetch`, the pattern of `ads/ads-chat.service.ts` (`ANTHROPIC_API_KEY`, `ANTHROPIC_API_URL`, model `CATALOG_IMPORT_MODEL` defaulting to the ads chat default), with one forced tool whose input schema is the extraction schema; 60 s timeout, one request, no retry. Output is validated with `zod` (already a dependency): `{lang, services: {title, titleAr?, description?, priceAmount?, currency?, durationMinutes?}[], staff: {title, role?, workingHours?: {day, from, to}[]}[]}`, capped at 100 services and 50 staff (`MAX_PROPOSED_SERVICES`, `MAX_PROPOSED_STAFF`, Tkana). A duration or hours the source does not state stay absent (the prompt says so; the review step fills a default duration of 60 that the user sees). The input text and the model output are never logged.
  - **Review:** `proposal = {items: {key, kind: "service"|"staff", data, duplicateOf: {id, name} | null, selected}[]}` stored on the row. Duplicates = same normalized name (trim, collapse spaces, Latin lowercase, Arabic normalization: strip tatweel and diacritics, unify `أ/إ/آ → ا`, `ى → ي`, `ة → ه`) as a non-archived catalog row or an earlier item; duplicates start `selected: false`. `PATCH /catalog-imports/:id/items` edits data and selection (validated: duration 5–1 440, price ≥ 0, schedule via `validateSchedule`).
  - **Run:** `POST /catalog-imports/:id/run` → `running`; `CatalogImportRunner` processes selected items in order. Each item's create and the `processed` increment are one transaction, so a crash never creates an item twice. Heartbeat every batch; `CatalogImportResumeScheduler` (`@Cron(EVERY_MINUTE)`, re-entrancy guarded, claim by compare-and-set on `heartbeatAt`, the SP-03 pattern) resumes a stale job. Staff items link services named in the same import or already in the catalog; a missing service name is a row error, not a failure.
  - **Templates:** `GET /catalog-imports/templates/:kind` (`kind = services|staff`) streams an `.xlsx` built with `exceljs` (approved D1), bilingual header notes, one example row.
- **MCP tools (ruling 10).** `create_appointment`/`update_appointment` accept optional `serviceId`/`resourceId`; the transition table, fit and `SLOT_TAKEN` errors come back to the agent as tool errors. New read tools `list_services` (active services with durations) and `find_slots` (`GET /bookings/availability` semantics). The agent prompt in `l-agent-setup.service.ts` gains two lines ("use find_slots before booking a catalog service"); setup re-sync is the existing flow.

## Global Constraints
- **Data (exact names; later SPs build on them):**
  ```
  /// SP-10: a bookable service.
  model Service {
    id          String    @id @default(cuid())
    workspaceId String
    workspace   Workspace @relation("WorkspaceServices", fields: [workspaceId], references: [id], onDelete: Cascade)
    name        String
    nameAr      String
    color       String    @default("info") // the StageColor keys: ink | info | ok | warn | bad | accent | human
    durationMin Int
    price       Decimal?  @db.Decimal(12, 2)
    currency    String    @default("SAR")
    active      Boolean   @default(true)
    archivedAt  DateTime?
    order       Int       @default(0)
    version     Int       @default(0)
    createdAt   DateTime  @default(now())
    updatedAt   DateTime  @updatedAt

    staff        StaffService[]
    appointments Appointment[] @relation("AppointmentService")

    @@index([workspaceId, active])
  }

  /// SP-10: a person (or chair/room) that bookings are placed on.
  model StaffResource {
    id          String    @id @default(cuid())
    workspaceId String
    workspace   Workspace @relation("WorkspaceStaffResources", fields: [workspaceId], references: [id], onDelete: Cascade)
    userId      String?   // the workspace member, when this resource is one
    user        User?     @relation("StaffResourceUser", fields: [userId], references: [id], onDelete: SetNull)
    name        String
    nameAr      String?
    role        String?   // free label, e.g. "Stylist"

    schedule    Json      @default("{}") // WeeklySchedule
    active      Boolean   @default(true)
    archivedAt  DateTime?
    version     Int       @default(0)
    createdAt   DateTime  @default(now())
    updatedAt   DateTime  @updatedAt

    services     StaffService[]
    appointments Appointment[] @relation("AppointmentResource")

    @@unique([workspaceId, userId])
    @@index([workspaceId, active])
  }

  /// SP-10: which services a resource provides.
  model StaffService {
    resourceId  String
    resource    StaffResource @relation(fields: [resourceId], references: [id], onDelete: Cascade)
    serviceId   String
    service     Service       @relation(fields: [serviceId], references: [id], onDelete: Cascade)
    workspaceId String
    createdAt   DateTime      @default(now())

    @@id([resourceId, serviceId])
    @@index([serviceId])
  }

  model Appointment {
    // … existing fields unchanged (service, serviceAr, staffId, status, HJZ columns, statusChangedAt) …

    serviceRef Service?       @relation("AppointmentService", fields: [serviceId], references: [id], onDelete: SetNull)
    resourceId String?
    resource   StaffResource? @relation("AppointmentResource", fields: [resourceId], references: [id], onDelete: SetNull)
    /// SP-10: optimistic-concurrency counter (Review Focus 4). `main`'s writes do not bump it.
    version    Int            @default(0)

    @@index([workspaceId, startAt])
    @@index([workspaceId, resourceId, startAt])
    @@index([workspaceId, serviceId])
  }

  /// SP-10: one catalog import (ruling 1). Not an ImportJob.
  model CatalogImport {
    id          String    @id @default(cuid())
    workspaceId String
    workspace   Workspace @relation("WorkspaceCatalogImports", fields: [workspaceId], references: [id], onDelete: Cascade)
    createdById String?
    createdBy   User?     @relation("CatalogImportCreatedBy", fields: [createdById], references: [id], onDelete: SetNull)

    kind        String    // "auto" | "services" | "staff"
  ```

## Architecture Rulings and Risks
Each item names the risk, then the recommended ruling. Items marked **(needs controller ruling)** are repeated under Controller rulings, where the controller fills in the decision.

1. **Catalog import storage: `ImportJob` or its own table.** The roadmap says `POST /imports` with `kind:"catalog"` reuses SP-03's `ImportJob`. But the deployed `main`, sharing the production database, runs `ImportResumeScheduler.sweep` every minute over **every** `running` job with a stale heartbeat and would hand a catalog job to its contacts runner; its `sweepAbandoned` cancels `uploaded/previewed` jobs and deletes their file; and its `GET /imports` lists every kind in the contacts import history. `ImportJob.fileMediaId` is also `NOT NULL`, which a paste or URL import has no value for.
   - **Ruling:** a separate `CatalogImport` table and `/catalog-imports` routes, reusing SP-03's code (`parseFile`, the lease/heartbeat/resume pattern), not its table. New code also filters `GET /imports` to `kind IN ('contacts','audience')`.
   - **Alternative:** `ImportJob` with `kind = "catalog"` after `main` is replaced, with `fileMediaId` made nullable (an `ALTER COLUMN … DROP NOT NULL`, which `main`'s client would mis-type). Unsafe until SP-10 ships and blocks verification on production. **(needs controller ruling)**
2. **Legacy bookings.** Existing rows have only free-text `service`/`serviceAr` and maybe `staffId`.
   - **Ruling:** no backfill. Legacy rows stay free-text (shown with their snapshot name and "Not in catalog" / "خارج الكتالوج"), are not fit-checked (`fit: "unchecked"`), but **do** block slots of the member's resource and show conflicts. A one-off "link to catalog" tool (by exact name) is a follow-up.
   - **Alternative:** a rerunnable backfill linking rows whose `service` equals a catalog name. **(needs controller ruling, minor)**
3. **Race protection.** Tkana uses an advisory lock plus a Postgres `EXCLUDE` constraint.
   - **Ruling:** the advisory lock per resource (and the member key for legacy staff bookings), taken by every new-code writer, with the overlap re-check inside the transaction. No `EXCLUDE` constraint: it needs the `btree_gist` extension, a generated range column and would refuse the deployed `main`'s overlapping writes and existing overlapping rows.
   - Accepted risk: `main`'s writes during the rollout window take no lock (it has no resources anyway).
   - **Alternative:** add `btree_gist` + `EXCLUDE … WHERE (status IN ('pending','confirmed') AND "resourceId" IS NOT NULL)` after SP-10 ships and data is clean. **(needs controller ruling)**
4. **Members, resources and legacy callers.** The AI agent (MCP `create_appointment`) and the current Calendar dialog book with `staffId` only.
   - **Ruling:** when `staffId` names a member with an active `StaffResource`, the writer resolves that resource and applies fit and overlap. Bookings by members without a resource, and bookings with no staff, are unchanged. Availability counts legacy bookings of the member as blocking.
   - Effect: the agent can now get `SLOT_TAKEN` or `outside_schedule` for a catalog member; the tool returns the error and the prompt already says "if a tool call fails, say so honestly".
   - **Alternative:** gate only writes that pass `resourceId` explicitly (the agent can double-book a catalog member). **(needs controller ruling)**
5. **"Appointments synced from HJZ bypass the fit gate."** Our code has **no** HJZ → CRM booking writer: HJZ sync is CRM → HJZ only (`HjzAppointmentSyncService`); HJZ-linked rows are ordinary CRM bookings with `hjzAppointmentId` set.
   - **Ruling:**
     - `booking-writer.ts` accepts `{bypassFit: true}` for internal callers (a future HJZ inbound, SP-23 connectors); bypassed rows skip fit and overlap and show `conflict`/`fit` on read;
     - an edit of an HJZ-linked row that does not change time, duration or resource (e.g. a status change pushed back) is never re-gated;
     - the HJZ payload is unchanged (names from the snapshot, staff from `staffId`).
   - **Alternative:** treat rows with `hjzAppointmentId` as bypassed for every edit. **(needs controller ruling)**
6. **Schedule shape and the unconfigured case.**
   - **Ruling:** the roadmap's `{mon:[{from,to}]}`, ≤ 3 windows a day, no overnight windows (split across days), `24:00` allowed as an end. A resource with no window on any day is **unconfigured**: manual bookings are not fit-gated (the UI warns "Schedule not set") and availability offers no slots (Tkana: unconfigured is "not set up yet", not seven days off). Breaks are gaps between windows.
   - **Alternative:** unconfigured = always closed (reject every booking). **(needs controller ruling)**
7. **Slot policy.**
   - **Ruling:** a fixed 15-minute step; no buffers, no minimum lead time beyond "not in the past", horizon 365 days; back-to-back bookings allowed. Buffers and lead time per service are a follow-up (Tkana has them).
   - **Alternative:** step = the service duration (Tkana default), or add `bufferBeforeMin/bufferAfterMin` columns now (additive, unused until set). **(needs controller ruling, minor)**
8. **Status values and transitions.**
   - **Ruling:** keep our five values (`no-show` with a hyphen, as stored today; the MCP enum and the Calendar use it). No `rejected` (a declined request is `cancelled`). The table is enforced for every caller; there is no reopen of a final booking. A mistaken "completed" is corrected by a new booking.
   - **Alternative:** allow `bookings.manage` to move a final booking back to `confirmed` within 24 h (would weaken the acceptance only for managers). **(needs controller ruling)**
9. **Website URL import.** A server-side fetch of a user URL is an SSRF vector.

   - **Alternative:** drop URL import from SP-10 and keep paste + file. **(needs controller ruling)**
10. **AI provider and the agent tools.**

13. **The list endpoint today returns every booking.** `GET /appointments` with no params loads the workspace's whole history (the Calendar does this).
